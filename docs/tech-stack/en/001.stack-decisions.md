# Acostator — Tech Stack Decisions

## Overview

This document records every technology choice made for Acostator, including the rationale and alternatives considered. Update this document whenever a significant dependency is added, upgraded, or replaced.

---

## Runtime: Cloudflare Workers

**Choice:** Cloudflare Workers (V8 isolate, not Node.js)

**Why:**
- Native bindings to D1 and R2 — no network hop between app and storage
- Edge deployment — low latency globally
- No server to manage
- Generous free tier for a research tool

**Alternatives considered:**
- Node.js on VPS — more familiar but requires server management
- Next.js on Vercel — no native D1/R2, would need external DB
- Bun on Fly.io — good DX but still requires server management

---

## API Framework: Hono

**Choice:** Hono v4

**Why:**
- Built specifically for edge runtimes (Workers, Deno, Bun)
- Zero Node.js dependencies — runs natively on V8 isolate
- Typed routing with RPC mode — can share types with frontend
- Middleware ecosystem (CORS, JWT, rate limiting)

**Alternatives considered:**
- Next.js API routes — requires `@cloudflare/next-on-pages` adapter, added complexity
- itty-router — simpler but less features, no typed middleware
- Express — Node.js only, does not run on Workers

---

## Frontend: React + Vite

**Choice:** React 19 + Vite 6

**Why:**
- Annotation tool is highly interactive — React's component model fits well
- SPA is sufficient — no SSR needed, all data fetched after auth
- Vite is fast for development iteration
- Large ecosystem for UI primitives (shadcn/ui, Radix)

**Alternatives considered:**
- Solid.js — better performance but smaller ecosystem
- Svelte — less familiar, fewer UI component libraries
- Vue — viable but team preference for React

---

## Database: Cloudflare D1 (SQLite)

**Choice:** Cloudflare D1

**Why:**
- Native Workers binding — no connection pooling, no latency
- SQLite is relational — fits our hierarchical schema (project→row→quadruple)
- Acostator is read-heavy with moderate writes — SQLite handles this well
- Free tier covers research-scale usage

**Limitations acknowledged:**
- D1 is not suited for high-concurrency write-heavy workloads
- SQLite has no native full-text search (use Drizzle `like` for category fuzzy search)
- Max DB size 10GB (sufficient for annotation metadata — actual CSV files go to R2)

**Alternatives considered:**
- Cloudflare KV — not relational, bad fit for complex queries
- Neon (PostgreSQL) — better for write-heavy but adds network latency from Workers
- PlanetScale — MySQL, adds complexity, external dependency

---

## File Storage: Cloudflare R2

**Choice:** Cloudflare R2

**Why:**
- No egress fees — important for large CSV downloads/exports
- Native Workers binding — direct access without HTTP
- Max object size 5GB (well above our 1GB CSV limit)
- S3-compatible API if migration is ever needed

**Upload strategy:**
- Files are uploaded directly from the browser to R2 via a presigned URL
- This bypasses the Workers 100MB request body limit
- Worker generates the presigned URL and handles post-upload processing

**Alternatives considered:**
- Cloudflare KV — 25MB value limit, not suitable for CSV files
- AWS S3 — adds external dependency and egress costs
- Local filesystem — not available on Workers

---

## ORM: Drizzle ORM

**Choice:** Drizzle ORM

**Why:**
- Only mature ORM with first-class Cloudflare D1 support
- SQL-like query builder — no magic, queries are predictable
- TypeScript-first schema definition
- Lightweight — no runtime overhead unlike Prisma

**Alternatives considered:**
- Prisma — does not support D1 natively (requires workarounds)
- Kysely — good SQL builder but no migration tooling
- Raw D1 queries — viable but loses type safety and migration management

---

## Auth: GitHub OAuth (manual implementation)

**Choice:** Manual GitHub OAuth flow in a Hono middleware

**Why:**
- NextAuth.js requires Node.js runtime — does not run on Workers
- Auth.js (v5) has experimental Workers support but is not production-ready
- GitHub OAuth flow is straightforward to implement manually
- Session stored as a signed JWT in an HTTP-only cookie

**Session strategy:**
- JWT signed with a `AUTH_SECRET` env variable
- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`
- JWT payload: `{ userId, githubId, username }`
- Expiry: 30 days, refreshed on activity

**Alternatives considered:**
- Cloudflare Access — adds infrastructure dependency, overkill for a research tool
- Auth.js on Workers — experimental, not production-ready
- Lucia Auth — viable but adds a dependency; manual is simpler here

---

## Styling: Tailwind CSS v4

**Choice:** Tailwind CSS v4

**Why:**
- Utility-first — fast iteration on annotation UI
- v4 uses CSS-first config (no `tailwind.config.js` needed)
- Works with Vite out of the box via `@tailwindcss/vite`

---

## UI Components: shadcn/ui

**Choice:** shadcn/ui (copy-paste components, not a package)

**Why:**
- Components are copied into the codebase — full control, no black box
- Built on Radix UI primitives — accessible by default
- Works with Tailwind CSS
- Key components needed: Dialog, Popover, Command (for category selector), Badge, Button

---

## Testing: Vitest + `@cloudflare/vitest-pool-workers`

**Choice:** Vitest with the Cloudflare Workers pool

**Why:**
- Tests run inside an actual Workers miniflare environment
- D1 and R2 bindings are available in tests — no mocking needed for DB queries
- Same test runner (Vitest) for both frontend and worker packages

**What to test:**
- Service layer functions (unit tests)
- Hono route handlers (integration tests with real D1)
- Annotation state machine transitions
- CSV parser edge cases

---

## Code Quality: Biome

**Choice:** Biome v1

**Why:**
- Single tool replaces ESLint + Prettier
- 10-100x faster than ESLint
- Zero config for TypeScript + React projects
- Enforces consistent formatting across monorepo

**Config:** `biome.json` at monorepo root, applies to all packages.

---

## CI/CD: GitHub Actions

**Pipeline:**
```
push / PR → biome check → tsc --noEmit → vitest → deploy preview (PR only)
merge to main → deploy to production
```

**Secrets required in GitHub:**
- `CLOUDFLARE_API_TOKEN` — for Wrangler deploy
- `CLOUDFLARE_ACCOUNT_ID`
- `GITHUB_CLIENT_ID` — GitHub OAuth app
- `GITHUB_CLIENT_SECRET`
- `AUTH_SECRET` — JWT signing secret

---

## Monorepo: npm workspaces

**Choice:** npm workspaces (built into npm, no extra tooling)

**Why:**
- Three packages only (`web`, `worker`, `shared`) — Turborepo is overkill
- Shared types package (`packages/shared`) avoids duplication between frontend and worker
- Scripts run from root: `npm run dev`, `npm run test`, `npm run lint`
